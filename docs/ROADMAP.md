# HeartBridge 下一阶段：从「能跑」到「有用」

写于 2026-09-01。前一阶段的目标是**工程可信**（131 测试、CI、可复现评测、安全层）。
这一阶段的目标是**内容可信**：让生成的回复真的值得发出去。

---

## 一、你观察到的三个问题，根因是三件不同的事

### 1. 「提问和回答都是固定的」→ 不是模型不行，是线上跑的根本不是模型

`streamlit_app/shared.py::is_demo()`：没配 API key 就返回 `MockProvider`，
回复来自写死的 `DEMO_OPTIONS`。你访问的 share.streamlit.io 上没有 key，
所以**你看到的每一条回复都是硬编码的示例**，不是 LLM 生成的。

这是刻意的设计（公开 demo 不该烧我的额度、不该把陌生人的对话发给第三方模型），
但 demo 模式的提示语写得太轻了，你自己都被骗过去了 —— 那对招聘方也一样。

**要做**：demo 模式的 banner 提到页面正中，并在每条回复卡片上直接标「示例，非实时生成」。
另外做一个 30 秒的本地录屏放进 README，证明真实模式长什么样。

### 2. 「盲评表是空的」→ LLM 通道不通，而失败被静默吞掉了

`generate_options` 在 `LLMError` 时 `return []`。对线上这是对的降级
（宁可不给建议，也不给编造的建议），但对评测脚本是灾难：
**「20 个情境全部调用失败」和「模型认真回答但一条都不合格」产出一模一样的空报告。**

已修：`scripts/eval_generation.py` 现在先打一发预检请求，通道不通就大声失败并打印
真实错误；即使通道通了但零条候选，也会明确告诉你是校验挂了而不是没跑。

> 顺带一个评测方法论的原则，值得写进面试话术：
> **评测工具必须能区分「系统坏了」和「系统表现差」。** 分不开的时候，
> 一份 0/0 的报告会被读成结论。

### 3. 「回复太空，全是『我在』」→ 一半是知识库，一半是 prompt 在承诺知识库给不出的东西

`generator.py` 的 system prompt 要求「生成 2-3 个**风格不同**的选项
（偏共情 / 偏陪伴行动 / 偏轻）」，但检索回来的 top-3 里，能支撑「行动」和
「轻」的卡片很少。模型只能拿着三张共情卡去凑三种风格，于是三条都塌回「我在」。

**prompt 承诺了知识库供不起的多样性。** 这是 RAG 应用里很典型的一类失配，
而且只有把生成和检索一起看才看得出来。

现有 30 张卡里其实已经有 `comm_009`（把标准降到地板高度）、`comm_020`（共同活动）、
`comm_007`（打断反刍）—— 行为激活的骨架是有的。真正缺的是下面第三节列的那几类。

还有一个检索质量的信号：16 个情境的 top-3 里，`comm_017`（看见好转但不设新基线）
命中了 **6 次**，`comm_004`（低压力在场）命中 **6 次**。一张讲「好转期期待管理」的卡
成为三分之一情境的最佳匹配，这不是它真的相关，是知识库太稀、检索被迫拿它凑数。
**扩库本身就会改善检索**，这条可以在扩库前后各跑一次 `eval_retrieval.py` 量出来。

## 二、缺的模块之一：陪伴者关怀（你问的「特殊部分」）

**现状：没有。** `core/care/` 是个空目录，只有一张 `comm_019`（照顾者耗竭）孤零零挂在沟通卡里。

这是整个项目最值得补、也最好讲的一块。理由：

> 市面上每一个「如何陪伴抑郁症患者」的工具，都把使用者当成**工具**——
> 教他怎么当一个更好的照顾者。没有一个把使用者当成**病人的第二个病人**。
> 而照顾者负担（caregiver burden）是有文献、有量表、有临床共识的真实构念。

### 设计

**(1) 第三种卡片类型 `boundary`**

schema 和沟通卡平行，但受众是使用者自己。场景写成使用者会怎么描述自己的处境：

- 「他半夜三点说不想活了，我第二天早上有考试」
- 「我一说我今天很累，他就说『那你走吧』」
- 「我已经三个月没跟朋友出去过了」
- 「我发现我开始不想看他的消息」← 这条最重要，是耗竭的早期信号
- 「他好一点了，但我反而崩溃了」← 照顾者的崩溃常常延迟到危机结束后

字段沿用 do / dont / example_phrases / why_it_works，但多两个：
- `self_check`：一句让使用者判断「这条是不是在说我」的自检问题
- `not_abandonment`：明确写清楚「这样做为什么不是抛弃他」——
  这是使用者最大的阻力，不写清楚卡片就是废的

**(2) 耗竭检测器 `core/care/depletion.py`**

结构上和 `core/safety/detector.py` 同构（规则优先 + 升级才调模型），
但扫描的是**使用者自己写的那段话**，不是伴侣说的话。

信号分层：
- `RESENTMENT`：「凭什么」「我也很难受但没人管我」「我受够了」
- `SELF_ERASURE`：「只要他好我怎样都行」「我不重要」「我不该有情绪」
- `ISOLATION`：「没人能理解」「我不敢跟朋友说」
- `OWN_RISK`：使用者自己出现危机信号 → **直接走危机分支**，这条必须有

命中后**改变产品行为**，不是加一句提示：不再给「怎么回复他」的话术，
先给一屏「你现在需要的不是话术」。这是把安全层的哲学（在便宜的方向上犯错）
用第二次。

**(3) 第 4 个 Streamlit 页面：`4_照顾自己.py`**

+ 会话结束后一个轻量 check-in：「你现在还剩多少力气？1-5」，本地存，画趋势。
  不是 gamification，是让使用者看见自己在往下掉——耗竭的特征就是当事人最后一个发现。

**(4) 评测**

耗竭检测和危机检测一样，做一套人工标注集（建议 30-40 条，含对抗样本：
「我快累死了」是口语不是耗竭），报 recall / false-positive rate，进 CI 当发布门禁。
**这样这个模块从第一天就带着数字，而不是一个 feature 描述。**

## 三、缺的模块之二：memory（你要的个性化）

**现状：`PartnerProfile` 是一张手填的静态表单**，字段固定，填完就不动了。
它能让回复带上他的名字和雷区，但产生不了「我们的故事」。

### 设计：两层记忆 + 人在回路的写入

**语义层（semantic）** = 现在的 profile。稳定事实：雷区、有效过的安慰、诊断、异地与否。
体量小，**每次都全量注入 prompt**。

**情节层（episodic）** = 新增。带日期的事件记录：
```json
{"date":"2026-03-12","situation":"工作汇报前一晚崩溃",
 "what_i_did":"没劝，陪他下楼走了半小时","outcome":"有效","confidence":0.8,
 "evidence":"原始对话片段"}
```
体量会持续增长，**不能全量注入**——所以它是**第二个检索语料**。

> 这是整个设计里最漂亮的一步：**你已经有检索器了。**
> 让「你们的历史」复用同一个 `Retriever`，生成时同时检索
> 知识卡（通用技巧）和情节记忆（这次是不是以前遇到过）。
> 于是回复可以是：「上次他这个状态，你陪他走路管用了 —— 要不要再来一次」。
> 这条建议**是有出处的、可校验的**，和现有的 card_id 校验完全同构。
> 个性化因此没有变成幻觉的新入口。

**写入必须人在回路。** 会话后由抽取器提出候选记忆，用户看到一屏
「我记住这些？」+ 勾选框，勾了才落库。理由有三条，都能讲：
1. 隐私：静默记录伴侣的精神健康信息是不可接受的
2. 准确性：抽取会错，而错误的记忆会污染之后**每一次**生成
3. 产品：使用者亲手确认过的记忆，他才会信任基于它的建议

**必须处理的两件事**（这两件是记忆系统的真正难点，面试会追问）：
- **冲突**：新记忆和旧记忆矛盾时留哪个（策略：都留，标 `superseded_by`，
  检索时优先近的——因为人是会变的）
- **衰减**：半年前的雷区今天可能不是了。加 `last_confirmed` 字段，
  超过 N 天的记忆在注入时降权并触发复核。

**评测**：记忆抽取的 precision = 用户勾选通过的候选 / 全部候选。
这是一个可以直接量的数字，而且低了就说明抽取器在编。

## 四、缺的模块之三：知识库真正缺的那几类卡

你的判断是对的：光强调「在场」不够。但要说清楚一件事，
否则这个方向会做歪，也会在面试里被问穿：

> **你没法把一个人从抑郁里「劝」出来。** 直接反驳负面认知会被解读为
> 「你不理解我的痛苦」，把对话变成辩论，他要花力气证明自己确实不配——
> 这就是 `comm_001` 写的。
>
> 但「只能共情、什么都不能推」也是错的。伴侣**能**做的有证据支持的事有三类，
> 现在的知识库都太薄：

**(1) 行为激活（Behavioral Activation）** —— 单个证据最强的、伴侣真的能参与的干预。
核心机制是**动作先于情绪**，直接反转「等有动力再做」这个维持抑郁的陷阱。
`comm_009` / `comm_020` 是起点，但需要扩到：怎么定一个小到不可能失败的动作、
失败了怎么不变成新的自证失败、怎么在异地做。

**(2) 引导式发现（guided discovery / 苏格拉底式提问）** —— **这就是你要的「换位思考」，
但必须以提问的形式，永远不能以反驳的形式。** 不是「你明明很好」，
而是「如果是我说自己一无是处，你会怎么跟我说？」——让他自己找到反例。
这类卡现在**一张都没有**，是最大的空缺。

**(3) 希望的具体化** —— 「会好起来的」是空头承诺，会被抑郁的认知过滤器自动删掉。
有效的希望是**具体、近期、可执行、且有你在场**：「下周三我们去那家店」。
`comm_015` 讲了「不许诺结果」，但没给「那该许诺什么」。

**(4) 一张路由卡：什么时候只在场，什么时候可以推一把** —— 你的抱怨本质上是
「它永远选在场」。判断依据（急性期 vs 平台期、他有没有主动提到未来、
`comm_012` 里他要的是听着还是想办法）应该本身是一张卡，让模型有东西可依。

**目标：+12~15 张卡，覆盖上面四类。** 扩库前后各跑一次 `eval_retrieval.py`，
`comm_017` 那种「一张卡命中六个情境」的现象应该消失——这是可量化的改善。

## 五、你那几个博主的视频怎么变成卡片

管道已经写好了，`core/ingestion/`：下载 → 本地 Whisper 转写 → LLM 蒸馏 →
Pydantic 校验（失败把报错喂回去自修）→ 用检索器查重 → 写到 `data/distilled/` 等人工复核。
**不会自动进知识库**，这是刻意的。

三条入口，按省事程度排：

```bash
source .venv/bin/activate

# A. 最快：你自己（或用任何转写工具）拿到文字稿，直接喂
python scripts/ingest.py --transcript-file ~/Desktop/blogger1.txt

# B. 抖音等 yt-dlp 支持的链接
python scripts/ingest.py --url "https://v.douyin.com/xxxx/"

# C. 小红书这类抓不到的：手机录屏/录音，走本地 Whisper
python scripts/ingest.py --audio ~/Desktop/clip.m4a --whisper-model small
```

然后 `data/distilled/*.json` 人工过一遍，合并进 `knowledge_base/cards/`。

**两个必须先做的调整：**

1. **蒸馏 prompt 现在只产 `communication` 卡。** 要加 `--card-type boundary`，
   否则博主讲的「怎么保护自己」全部会被硬塞成沟通技巧。

2. **加 `evidence_tier` 字段。** 现有卡的 `source.authority` 是 Beyond Blue 这种临床指南；
   博主内容是 practitioner 或 lived-experience。三档要分开标：
   `clinical_guideline` / `practitioner` / `lived_experience`。
   亲历经验**恰恰是**具体、不空、有真实语感的语料来源（你抱怨的「空」，
   临床指南是重灾区），所以要用；但必须标清楚，并且危机相关的卡只允许
   `clinical_guideline` 兜底。
   **这是一个负责任 AI 的点，而且是从产品需求里长出来的，不是贴上去的。**

## 七、这些做完，面试能讲什么

- **「你怎么发现回复质量差的」**：不是靠感觉。是盲测 A/B 对照 + 检索命中分布，
  发现一张卡吃掉了 1/3 情境的 top-3。
- **「你怎么定位的」**：三个症状（固定回复 / 空评测表 / 空话）根因完全不同：
  一个是降级路径没标清楚，一个是错误被静默吞掉，一个是 prompt 承诺了
  知识库供不起的多样性。**能把它们分开，本身就是答案。**
- **「个性化怎么不变成幻觉」**：记忆走检索、走引用校验，和知识卡同一套机制。
- **「你的 responsible AI 是什么」**：不是免责声明。是危机分支不生成文本、
  是记忆必须人工确认才落库、是证据分级、是把使用者本人也当成需要被监测的对象。
