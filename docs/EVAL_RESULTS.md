# 这一轮跑出来的结果（2026-09-01）

三件事：安全层补了一个盲区、生成评测第一次真的跑起来了、以及为什么它的
人工分数**还不能拿去写简历**。

---

## 1. 安全层：100% 召回是个错的数字

### 发现

第一版危机检测在 41 条评测集上拿到 crisis 召回 100%、误报 0%。这个数字是错的。

跑生成评测时，`g20`「我把猫送去我妈那儿养了 / 我照顾不好它」被规则层判成 `NONE`。
顺手试了几条同类的：

| 输入 | 旧规则判定 |
|---|---|
| 我把猫送去我妈那儿养了 | NONE |
| 我的东西你们看着分了吧 | NONE |
| 我写了封信放在抽屉里 | NONE |
| 谢谢你这两年，你要好好的 | NONE |

**整整一类信号，零覆盖。** 送走宠物、托付财物、留信、注销账号、弱式告别——
这些是自杀风险评估里标准的 warning signs，而且**往往一个「死」字都不含**。

### 根因，以及为什么它比 bug 本身重要

评测集和检测器是同一个人写的，于是**共享同一个盲区**：两边都在回答
「一个人会怎么用语言表达想死」，都没有回答「一个人在做准备时会说什么」。

> 100% 不是「已经很好了」，而是**「这个集合已经问不出新东西了」**。
> 一个指标的上限，是写这个指标的人的想象力上限。

这条比任何一个具体规则都值得记住，也是这次最该在面试里讲的东西。

### 修法

新增 `PREPARATORY_RULES`，定级 **ELEVATED 而不是 CRISIS**。这是刻意的：

> 「我把猫送去我妈那儿养了」完全可能只是因为下周搬家。
> 这类信号的**歧义是本质的**，不是规则写得不够好。

所以正确的处理不是让规则去猜，而是**保证它进入 LLM 二次确认**
（`assess()` 只在 level < CRISIS 时才调模型）。规则层负责「不要漏看」，
模型层负责「结合上下文判断」。**这是两级架构第一次真的被用上**——
在此之前它更像一个说得通的设计，现在它有了一个非它不可的场景。

同时加了 `_BENIGN_CONTEXT` 守卫（搬家/出差/生日/戒手机…）：命中准备性行为
但附近存在平凡解释时降一级，**但仍然记一条 `(良性语境降级)` 信号**——
降级不等于当没看见。这个守卫只对 PREPARATORY 生效，绝不碰 CRISIS 规则。

### 结果

评测集 41 → 53 条（+7 条真信号，+5 条**对抗性良性样本**——后者是这次补丁的
代价，必须和收益一起量，不能只报好消息）。

```
评测集: 53 条  (crisis 14 / elevated 15 / none 24)
  crisis 召回率        14/14 = 100.0%
  误报率 (none→crisis)  0/24 = 0.0%
  降级错误 (crisis→低)  0
```

顺带补掉两条一直存在、但因为 CI 只 gate crisis 召回而**从没被看见**的
elevated 漏报（「这辈子都不会好了」「看不到任何希望了」）。
→ 待办：CI 的门禁应该同时 gate elevated 召回，否则这类漏报会继续隐形。

## 2. 生成评测：跑起来了，80 条待评

### 之前为什么是空的

`generate_options` 在 `LLMError` 时 `return []`。对线上这是对的降级
（宁可不给建议，也不给编的建议），但对评测是灾难：
**「全部调用失败」和「模型认真回答但都不合格」产出一模一样的空报告。**

已修：`_preflight()` 先打一发真实请求，通道不通就带着真实错误中止；
即使通道通了但零候选，也会明确说是校验挂了。

> **评测工具必须能区分「系统坏了」和「系统表现差」。**
> 分不开的时候，一份 0/0 的报告会被读成结论。

### cassette：让评测可复现

新增 `CassetteProvider`（`core/utils/llm.py`）。把一次真实 LLM 调用的
输入输出按 `sha256(system + 分隔符 + user)` 存下来，之后按输入哈希回放。

- 录一次 → 评测永久可复现，不要 key、不花钱、CI 里能跑
- **prompt 一改，哈希就对不上 → 硬失败**，不会拿旧回复冒充新系统
  （这条是关键：它让 cassette 没法变成自欺欺人的工具）
- 回放缺条目是 `LLMError`，不是静默降级

### 三个不需要人评就成立的结果

跑完 20 情境 × 2 组 × 2 条 = **80 条待评**。以下数字是代码算的，与评分无关：

| 组别 | 选项数 | 有引用 | 引用有效 | 引用是编的 |
|---|---|---|---|---|
| 有知识库 | 60 | 54 | 51 | **3** |
| 无知识库 | 60 | 3 | 0 | **3** |

**(a) 引用校验真的抓到了东西。** 有知识库组里有 3 条引用了**本次没检索到**的卡。
不是演的，是模型自然伸手去够一张它记得但这次没给它的卡。生产配置
（`drop_ungrounded=True`）会直接丢掉这 3 条。这就是「溯源是可执行的校验，
不是一句宣传」的实证。

**(b) 没有知识库时，引用 100% 是编的。** 无知识库组只有 3 条给出了 card_id，
**其中 0 条有效**。模型被要求标注出处、而手上没有出处时，它会**造一个**。
这是「检索器是屏障」这个设计最直接的证据。

**(c) 20 个情境里有 2 个，「有知识库」根本不成立。**
`g13`（今天居然自己爬起来了）和 `g16`（你会不会有一天也受不了我）
在 BM25 下**检索命中数为 0**。

这一条有个漂亮的旁证：cassette 里只有 **38** 条记录，不是 40。
因为这 2 个情境的两组 prompt **逐字节相同**——没有卡片可注入时，
「有知识库」组和对照组是同一个系统。哈希碰撞把它证明了。

> `g16` 是「你会不会有一天也受不了我」，而知识库里 `comm_018`
> 恰恰就是讲反复寻求保证的。**卡片存在，BM25 就是够不着**——
> 一个字都不重合。这是稀疏检索的典型失效，也是 dense 在 holdout 上
> 赢 BM25（76.7% vs 36.7%）的原因在单个例子上的样子。

## 3. 为什么这一轮的人工分数不能写进简历

**候选是 Claude 生成的，不是你的模型生成的。** OpenRouter 在两个可用的
执行环境里都被出口白名单挡掉了，所以没法用你的 key 真的跑一次。

这带来一个**方法论上必须承认的问题**：

> 盲评设计保证的是**评的人**不知道哪条来自哪组。
> 但这一轮里，**生成的一方知道假设是什么**。
> 「无知识库组」是由一个知道自己在扮演对照组的模型写的。
> 即使尽力保持诚实，这个 A/B 的结论强度也已经被削弱了。

所以：

- `cassette_reference.json` 命名带 `reference`，不是 `run_01`
- 这一轮的 `human_results.json` 只用来**看真实输出长什么样、练一遍评的流程**
- **可发布的数字必须来自你自己的模型**：key 能用之后跑
  `python scripts/eval_generation.py generate`（会自动预检），
  重新录一份 cassette，重评一次

上面第 2 节的三个数字 **(a)(b)(c) 不受这个问题影响**——它们是代码算的
结构性事实（引用有没有落在检索结果里、检索有没有命中），不是人的判断。

## 4. 你现在可以做的

盲评表在 `data/generation_eval/rating_sheet.md`，80 条，来源已隐藏、顺序已打乱。
每条只回答一个问题：**这一条我真的会原样发给他吗？** 填 Y 或 N。

填完跑 `python scripts/eval_generation.py score`。**填完之前不要看 answer_key.json。**

即使这一轮的数字不发布，**你还是应该亲手评一遍**——因为你会在评的过程中
直接看到「空话」长什么样、以及有卡和没卡的差别到底有多大。
那个体感会决定 ROADMAP 里 P1 那 12-15 张卡该怎么写。
